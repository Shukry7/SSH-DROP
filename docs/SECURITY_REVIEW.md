# Security hardening review — 2026-11-02

Scope: development source including saved profiles, automated regression tests, npm dependency advisories, packaging configuration, and CI. This is not an independent penetration test, cryptographic certification, full traffic inspection, memory-forensics assessment, or an assurance that all vulnerabilities are known.

## Implemented controls and evidence

- Electron sandbox and context isolation stay enabled; Node integration and webviews stay disabled. Permissions, navigation, and popup creation are denied. IPC validates the application window, main frame, expected page URL, and operation payload. Desktop tests exercise these restrictions and renderer fetch rejection.
- Renderer storage uses a nonpersistent session. Production DevTools are disabled. Main exposes individual application methods rather than generic shell/filesystem/IPC access.
- Server host identities are checked before authentication; changed identities and malformed/oversized trust stores block connection. Native confirmation is required for new trust.
- Passwords, passphrases, and key contents are not saved. Profile metadata remains intentionally unencrypted and is disclosed in the UI and privacy policy. Atomic bounded storage and a single-instance lock prevent ordinary concurrent application processes from overwriting one another's profile/trust changes.
- A terminal reset disposes the old xterm instance, including pending writes, on disconnect and before connecting. Transfer history clears, and late old-session transfer events are suppressed. Desktop tests verify the old terminal DOM is detached and history removed; this does not prove forensic memory erasure.
- SFTP listings use bounded batches rather than accumulating an unbounded `readdir(path)` result: 10,000 entries, 4 MiB of accounted filename/metadata data, 128 batches, and a 30-second deadline, with bounded best-effort handle cleanup. Invalid filenames and metadata are rejected. Unit tests include endless/empty batches, malformed names, excessive sizes, timeouts, stale sessions, and cleanup. SSH/SFTP parsing still depends on maintained third-party libraries.
- Private keys and transfers use native file selection and exclusive destinations. Existing overwrite, cancellation, host-trust, sandbox, and profile tests remain in the suite.
- Electron updated to 45.2.1. Packaged fuses disable Node mode, Node option environment variables, and Node inspection arguments; application code must load from ASAR, with embedded integrity validation enabled where supported. CI inspects actual packaged binaries and builds full installers on each OS. ASAR/fuses do not replace OS code signing; Linux does not provide the same embedded integrity enforcement as Windows/macOS.
- Official workflow Actions are pinned to commit SHAs. Dependency-policy and tracked-file secret gates run on every platform and release, with weekly monitoring once merged into the default branch. Scan errors fail rather than implying a clean result. Uploaded diagnostics use a restricted path list and synthetic fixtures.

## Remote file action controls

Remote file actions use strict action-specific IPC schemas and SFTP requests only. Main-process native confirmations default to Cancel and show quoted full paths. Delete is permanent and nonrecursive; symlinks/special files and root-like targets are refused. Canonical parent and source metadata are checked again after confirmation. File actions serialize against app transfers; each preflight/post-confirmation network phase has a 10-second deadline, excluding time spent reviewing confirmation. Interruptions after sending are reported as uncertain and never automatically retried or rolled back; network timeout closes the connection to isolate late replies. Standard rename refuses replacement under the [SFTP v3 specification](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02#section-6.5); the overwrite extension is not used. These checks cannot eliminate server-side races, identify every same-metadata replacement, protect against a malicious/nonconforming server, or prevent changes made through the terminal or another client. Use disposable paths and backups for critical data.

## Transfer reliability controls

Transfer reliability hardening stages into exclusive temporary sibling files, requests mode 0600, bounds setup/finalization and cleanup, and detects no-progress stalls independently of SSH keepalives. SHA-256 compares destination readback against the bytes observed in the source stream; it is not an independent trusted-server checksum, proof of server durability, or a transactional snapshot. Upload readback adds network traffic. Source size/metadata are rechecked, but same-metadata replacements, concurrent path races, compromised servers/accounts, and OS/filesystem behavior remain outside the guarantee. Upload publication relies on standard no-replacement SFTP rename; local downloads use hard links and fail safely on unsupported filesystems. Unacknowledged publication never triggers automatic retry or deletion of the final destination. Temporary files may remain after a lost open/close/publication acknowledgment, cleanup failure, or app crash. Interruption notices are generic and memory-only, preserving the privacy reset for filenames across connections.

## Verified replacement and recovery (0.2.0-alpha.2)

Conflict choices use main-owned native confirmations defaulting to Cancel. IPC recovery actions contain only a strict UUID and named action; native-selected local paths and server-bound records remain in main. Connection leases are rechecked after native pickers/approvals. Protected operations serialize against transfers and remote file changes. A verified independent local backup precedes replacement; the incoming file is staged and the destination hash/owner/group/mode rechecked. Upload replacement requires negotiated OpenSSH POSIX rename; no delete-first fallback exists. Windows uses a fixed native File.Replace script with paths passed only as environment data, an additional same-volume safety backup, and no ignored metadata-merge errors. The renderer receives no generic shell or filesystem API.

Bounded, versioned recovery records are written before publication, scoped to host key/address/port/account, and reloaded after restart. Unknown outcomes retain records/copies and require manual inspection; no automatic retry or rollback is attempted. Rollback verifies the stored backup and currently installed file, then independently backs up the current version before restoring the older ordinary contents. Changed destinations can be restored as separate copies. Backup deletion is explicit and blocked for unresolved records.

Backups and metadata are intentionally unencrypted and may contain secrets from the files themselves. Recovery files request Unix owner-only modes; Windows relies on application-data ACLs. SHA-256 covers ordinary contents only. Remote ACLs/xattrs/hidden hard links, alternate data streams, server dishonesty, cross-process compare-and-swap races and power-loss durability are not guaranteed. Backup restoration does not restore every filesystem attribute. Stop other writers and test disposable data; real-device ACL/crash/fault-injection review remains necessary before stable release. Existing `0.2.0-alpha.1` draft installers are unchanged.

The follow-up review of replacement code adds timestamp-only conflict detection, a second backup checksum check immediately before publication, and expected-backup checksum verification after restoring either a local or remote copy. Path validation runs before native warnings to prevent control/bidirectional-character spoofing; persisted modes cannot request special permission bits and recovery metadata must be a regular file. Disconnect clears connection-specific errors and controls, and connection-scoped callbacks suppress delayed recovery/transfer errors from an old session. Regression tests cover these failure paths, including a rejected native dialog after disconnect.

## Encrypted recovery (0.2.0-alpha.3)

New backup contents and metadata use AES-256-GCM, a random 256-bit vault key, and random 96-bit nonces. AAD binds each backup to its UUID/purpose, and metadata to a distinct stable purpose. A strict bounded key envelope contains only OS-wrapped key material. The vault refuses missing/corrupt keys instead of regenerating one over existing ciphertext. Key bytes are cleared when possible; JavaScript strings and OS/dependency memory cannot be reliably zeroed. Atomic encrypted metadata writes are fsynced, authenticated/read back, and renamed before legacy metadata is replaced with a non-sensitive incompatible-version marker. This is not a guarantee against power-loss or filesystem dishonesty.

Backup acquisition streams directly into encryption; restore/rollback streams decrypted bytes into exclusive staging and authenticates the complete stream plus recorded SHA-256 before no-replace publication. Corrupt or partial data cannot become a published recovery file. Remote reads/writes retain per-request deadlines and connection/cancellation guards. Unknown publication outcomes retain evidence without automatic replay. Existing destination files and native Windows same-volume safety copies remain ordinary plaintext by design.

OS protection is injected only in main. Windows/macOS use bounded asynchronous Electron safeStorage calls. Linux rejects `basic_text`, unknown and unavailable providers, using the recognized synchronous libsecret/KWallet provider because Electron 45's asynchronous provider selection can differ. This can block on an OS keyring prompt and needs replacement/review before an Electron upgrade removes the synchronous API. No renderer crypto, key, path-selection or generic filesystem capability is added. OS key rotation, portable export and recovery after OS account/key loss remain unimplemented. Same-user software and administrators remain outside the threat boundary.

Legacy files are migrated explicitly, per verified server-bound UUID. Encrypted content must verify before the record is marked encrypted, and metadata must commit before unlinking plaintext. Failed migration retains the original; retries replace only that record's unused encrypted migration output. Other legacy records/files survive. Encrypted records keep Secure backup available to retry interrupted plaintext cleanup. Storage limits and free-space reserve remain enforced. Older alpha.2 binaries cannot read the new encrypted journal and must not be used against a migrated backup folder; use a separate user-data directory when testing old versions. Migration is not secure erasure.

Regression tests cover ciphertext header/body/tag corruption, truncation/extra bytes, swapped UUIDs/purposes, empty/multi-chunk data, locked/unavailable providers, missing/corrupt/nonregular keys, interrupted encryption, failed metadata commits, migration retries, and authenticated staging. Windows recovery desktop tests use actual OS key protection, with unavailable-key behavior simulated; Linux/macOS CI mocks the provider. A separate Windows test verifies actual OS wrapping and unwrapping of a disposable value. Full DPAPI/Keychain/libsecret/KWallet lifecycle tests, Windows ACLs, signed identity, disk-full/crash behavior and an independent crypto review remain required before stable release.

## Dependency findings and temporary exception

The initial full npm audit reported 25 moderate findings, all stemming from [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249). Compatible modern minimatch copies are now overridden to patched 11.0.1. Do not use `npm audit fix --force`: npm suggests downgrading core build/lint tools and can break their APIs.

The raw report still lists 15 moderate transitive findings, rooted in four development-only paths using minimatch 3.1.5 or 5.1.9. Those implementations use an older callable CommonJS API and lack `firstPhasePreProcess`, `secondPhasePreProcess`, and the `optimizationLevel` preprocessing algorithm described in the advisory. Installed-version/API tests support this applicability assessment; it is not an upstream advisory correction or a claim that these packages have no other flaws.

`scripts/security-exceptions.json` records the exact advisory and versions, with expiry **2026-12-02**. The policy rejects other advisories, changed versions, production dependencies, high/critical findings, unknown advisory chains, expired exceptions, incomplete reports, and service failures. Raw findings remain visible in audit output and diagnostics. Review upstream-compatible replacements and the advisory again before expiry; do not extend the exception automatically.

Run `npm run security:audit`, `npm run security:secrets`, `npm run check`, `npm run test:e2e`, and, after packaging, `npm run security:package`. An npm production-only clean scan does not establish the safety of Electron's bundled Chromium/Node binaries or unknown vulnerabilities.
